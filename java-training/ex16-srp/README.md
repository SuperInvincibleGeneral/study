# 課題16: 単一責任の原則 SRP（難易度 ★★★★☆）

## この課題のねらい
ここから設計の課題に入る。**「動くけれど変更しづらいコード」を、変更しやすくする** 練習。
今回のテーマは SOLID の S、単一責任の原則（Single Responsibility Principle）。

## 状況
`work/SalesReport.java` の `printReport()` は、1つのメソッドの中で
1. 売上を **集計** し
2. 表示用の文字列に **整形** し
3. 画面に **出力** している

このため、次の要望に応えられない。
- 集計結果だけを別の画面で使いたい
- 出力先を画面からファイル・メールに変えたい
- 整形の仕方だけをテストしたい（画面出力を見ずに）

## 求められる構成（テストがこの名前で呼び出す）
| クラス | メソッド | 責務 |
|---|---|---|
| `SalesAggregator` | `int total(List<Sale>)` | 合計金額 |
| | `Map<String,Integer> byCategory(List<Sale>)` | カテゴリ別合計。**金額の降順、同額ならカテゴリ名の昇順** |
| | `String topCategory(List<Sale>)` | 最も売れたカテゴリ。空なら `""` |
| `SalesReportFormatter` | `List<String> format(Map<String,Integer>, int total)` | 行の並びを作るだけ。**出力しない** |
| `SalesReporter` | `List<String> report(List<Sale>)` | 集計役と整形役を組み立てる。**出力しない** |

出力フォーマット:
```
=== 売上レポート ===
Books : 5000
Food : 1200
合計 : 6200
```

## 手順
1. `work/` に上記のクラスを作る（`SalesReport.java` は削除してよい）
2. `./run.sh 16` （Windows は `run.bat 16`）

## 制約
- `test/` と `common/` は編集しない
- `Sale.java` はそのまま使う
- **`SalesAggregator` と `SalesReportFormatter` の中に `System.out` を書かないこと**
- `SalesReportFormatter` は `Sale` を知らないこと（集計済みの `Map` だけを受け取る）

## 自力で調べるためのポイント
- まず **「単一責任の原則」を自分の言葉で説明できるか** を確認する。
  よくある誤解は「1クラスに1メソッドだけ書くこと」。これは間違い。
  - 例: `単一責任の原則 とは 誤解`
  - 例: `SRP 変更理由 は1つ 意味`
- 判断に迷ったら、**「このクラスを変更したくなるのはどんなときか」を全部書き出す** とよい。
  2つ以上出てきたら分割の候補。
- 「なぜ `System.out.println` があるとテストしづらいのか」も考えること。
  - 例: `java テストしにくいコード 標準出力 依存`
- カテゴリ別の集計は自分で `if (map.containsKey(...))` を書く前に、標準のメソッドを探すこと。
  - 例: `java Map 集計 merge getOrDefault 使い方`
  - 例: `java Map 値でソート`
