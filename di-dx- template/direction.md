作成日: 2026-09-04

## 1. 目的

OpenAPI定義(YAML)の作成・修正をExcel上で行い、Pythonスクリプト経由でYAMLファイルを生成する仕組みを構築する。

### 解決したい課題

| 課題 | 内容 |
|---|---|
| エラー検出の遅さ | YAMLはテキストのため、Redoclyを実行するまでエラーが分からない |
| エラー内容の不明瞭さ | lintのメッセージが本質を示さず、修正箇所の特定が困難 |
| 作業負荷 | テキストベースで手書きする作業コストが高い |

---

## 2. 前提条件（ヒアリング済み）

| 項目 | 内容 |
|---|---|
| OpenAPIバージョン | 3.1系を使用中。ただし**バージョン指定により処理を分岐**させたい（旧バージョンのプロジェクト対応、将来のバージョンアップ対応） |
| YAMLファイル構成 | **複数ファイル分割** |
| エンドポイント数 | プロジェクトにより 5〜500 |
| 共通スキーマ | なし |
| 利用シーン | 新規作成 / 既存修正・追加の両方。**既存YAMLの読み込みが必要** |
| 実行環境 | Excelマクロ利用可。Python / バッチ / PowerShell も併用可 |
| Redoclyのlint設定 | **未確認** |

## 3. 決定した設計方針

### 3.1 アーキテクチャ

```
Excel(.xlsm)  <-->  Python  <-->  YAML(複数ファイル)
   入力UI          変換処理         成果物
   入力チェック          |
                        v
                 redocly lint (最終検証)
                        |
                        v
              エラーをExcelセルに書き戻し
```

### 3.2 役割分担

| レイヤ | 担当範囲 |
|---|---|
| Excel / VBA | 入力UI、プルダウンによる選択肢制限、入力チェック |
| Python | YAML読み書き、Excel読み書き、分割ファイル管理、Redocly実行と結果解析 |
| Redocly CLI | 最終検証 |

### 3.3 採用ライブラリ（方針）

- **ruamel.yaml**: YAML読み書き。コメント・キー順・引用符スタイルを保持できる（PyYAMLでは失われる）
- **openpyxl**: PythonからExcelを直接読み書き。中間CSVは不要

### 3.4 VBAでYAMLパースを行わない理由

- VBAにYAMLパーサーが存在せず、自前実装が必要になる
- OpenAPI YAMLで使われる構文（アンカー `&`/`*`、複数行文字列 `|` `>`、フロースタイル `{}` `[]`）を全て処理する実装は、それ自体が大規模な開発対象となる

## 4. Redoclyバージョン固定の方針

lintのチェック内容は以下2要因で変動するため、バージョンを固定できる設計とする。

1. **ルールセット**: `redocly.yaml` の `extends`（`minimal` / `recommended` / `spec` 等）および個別ルールの上書き
2. **Redocly CLI自体のバージョン**: 新ルール追加、既定ルールセットの変更、既存ルールの挙動変更が起こり得る

### 実現手段

**方法1: npx でバージョン指定実行**

```bash
npx @redocly/cli@1.25.11 lint openapi.yaml
```

インストール不要。プロジェクトごとにバージョンを使い分けるのに適する。

**方法2: package.json で固定**

```json
{
  "devDependencies": {
    "@redocly/cli": "1.25.11"
  }
}
```

`npm ci` で厳密に再現。チーム全員が同一バージョンを使う場合はこちら。

### 注意点

- npx はネットワーク接続が必要。クローズド環境の場合は事前キャッシュか方法2を採用
- Node.js のインストールが前提。Redocly CLI のバージョンにより要求Nodeバージョンが異なる

## 6. エラー分かりづらさへの対策

### 6.1 なぜ分かりづらいのか

- Redoclyのエラーは `$ref` 解決後の構造ツリー上の座標で報告される。分割ファイル構成では、元ファイルのどこを直すべきかが直感的に結びつかない
- 根本原因から離れた場所でエラーが出ることがある（例: `$ref` 先のtypo → 参照元で「schema不正」として報告）

### 6.2 改善できること

**位置特定の解消**

`redocly lint --format=json` の出力には、エラー箇所のファイルパスとJSONポインタが含まれる。これをPythonでパースし、Excelの該当セルに直接色付け＋メッセージ表示する。「どのエンドポイントの、どの項目か」がセル単位で判明する。

**メッセージ変換テーブル**

頻出エラーは変換辞書を持たせる。繰り返し出るエラーは数十種類程度に収束すると見込まれる。

| Redoclyの出力 | 変換後の表示 |
|---|---|
| `Expected type 'object' but got 'null'` | 必須項目が空です |
| `Can't resolve $ref` | 参照先スキーマが存在しません |

### 6.3 改善できないこと

- 未知のエラー、新バージョンで追加されたルールのメッセージ
- 根本原因が離れた場所にあるケース（表示位置は正確にできても、真因特定は人の判断が必要）

### 6.4 本命の対策

Excel側で構造を強制する（パス・メソッド・パラメータをプルダウンと定型列で入力させ、YAMLは生成のみ）ことで、手書き起因のエラーを大半排除する。lintは最終確認の位置づけとする。作業負荷の課題にも同時に効く。

## 7. Excel側チェックの範囲

### 担保可能

- 必須項目の未入力チェック
- パス記法（`/users/{id}`）とパラメータ定義の整合チェック
- HTTPメソッド・型・formatのプルダウン制限
- `$ref` 参照先スキーマの存在チェック
- 重複 operationId 検出
- YAMLのインデント・クォート・特殊文字エスケープ（生成ロジックで完全制御）

### 担保しない

バージョン依存のスタイル系ルールをExcel側に実装するのは、コストが高い割に追従が困難。以下の役割分担とする。

- **Excel側**: 仕様違反レベル（どのバージョン・ルールセットでも共通してエラーになる部分）のみ
- **バージョン依存部分**: Redoclyの実行結果をセルに書き戻す

### 動的切り替え（オプション）

プロジェクトの `redocly.yaml` をPythonが読み、有効なルールに応じてExcel側チェックを切り替える設計も可能。ルールセット差分にある程度追従できる。

## 9. 未確定・要確認事項

### 9.1 次セッションまでに用意するもの（ユーザー作業）

以下を既存プロジェクトで実行し、出力を連携する。

```bash
# 1. バージョン確認
redocly --version

# 2. JSON形式で詳細出力
redocly lint --format=json openapi.yaml > errors.json

# 3. エラーの位置を確認（errors.jsonをテキストエディタで開く）
#    "location.file" と "location.pointer" を見ると、
#    どのファイルの、どこを示しているかが分かる
```

**連携が必要な情報**

1. `redocly --version` の出力
2. `redocly lint --format=json` の出力（errors.json）
3. 既存プロジェクトのディレクトリ構成（`tree` の出力可）
4. `redocly.yaml` の内容（存在する場合）

**理由**: これらが無いと「エラーゼロ」の基準が定義できず、シート構成の具体設計に進めない。またメッセージ変換テーブルに何を入れるべきかが確定しない。

### 9.2 分割ファイル構成に関する未解決の設計論点

複数ファイル構成では以下の決定が必要。ディレクトリ構成の実物を見てから判断する。

| 論点 | 内容 |
|---|---|
| 行とファイルの対応 | 出力時にファイルへ書き戻すため、各行が「どのファイルの、どのパス」由来かを保持する列が必須 |
| `$ref` の扱い | 参照を解決して展開するか、参照文字列のまま持つか。**後者を推奨**（元の分割構造を壊さないため） |
| 新規追加時の出力先 | どのファイルに書くかを行ごとに指定させるか、規約で自動決定するか |
| 分割の粒度 | タグ単位かリソース単位かで、シート設計が変わる |

### 9.3 実行環境の確認事項

- 各利用者のPCにPythonをインストール可能か
- 不可の場合、PyInstaller で単一exe化する方針となる

## 10. 開発フェーズ案

### フェーズ1: 出力専用ブック

Excel → YAML の一方向。バージョン（3.0.x / 3.1.x）をInfoシートで指定し、生成ロジックを分岐。既存ファイルは扱わない。

### フェーズ2: 読み込み機能の追加

対象を限定して実装する。

- 単一ファイル、またはアンカー未使用の分割ファイル
- Excelで表現できる範囲のキーのみ
- 範囲外のキーを検出した場合は**警告して読み込み中止**（黙って落とさない）

**ラウンドトリップ時の注意**: Excel経由で読み込み→再出力すると、Excelシートで表現していない拡張フィールド（`x-` 独自項目、`servers`、`security`、`callbacks` 等）が消えるリスクがある。ruamel.yaml の採用と、上記の警告機構で対処する。

1. 9.1 の連携情報を受領

5. フェーズ1の実装着手
